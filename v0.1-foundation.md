# v0.1 Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first safe, testable desktop foundation of Local Knowledge IDE: open one local folder, show a basic file tree, open a Markdown file in a CodeMirror source editor, and atomically save it back through the Rust filesystem boundary without introducing any proprietary storage.

**Architecture:** Tauri 2 hosts a React + TypeScript + Vite frontend. The frontend owns presentation and editor state; all real filesystem access goes through typed Tauri commands backed by Rust services. v0.1 intentionally implements only one opened root folder and Source Mode; Workspace multi-mount, Preview, Properties, indexing, graph, plugins, sync, and AI remain outside scope.

**Tech Stack:** Tauri 2, React, TypeScript, Vite, CodeMirror 6, Zustand, Vitest, Testing Library, Rust, serde, thiserror, tempfile.

**Spec:** `AGENTS.md` / `docs/PROJECT_MASTER_SPEC.md`, especially sections 0, 2–10, 26–39.

## Global Constraints

- Local files are the source of truth.
- Markdown content must remain ordinary `.md` files.
- SQLite is not introduced in v0.1.
- React must not read or write arbitrary filesystem paths directly.
- Filesystem access must pass through Rust commands/services.
- Saving must be atomic and must not truncate the original file before replacement succeeds.
- Existing line endings must be preserved for files opened and saved without deliberate conversion.
- Existing UTF-8 BOM state must be preserved.
- External modification must be detected before overwrite.
- No cloud, account, telemetry, AI, plugin store, graph, database view, sync, LaTeX compilation, Live Preview, Typora-like mode, or multi-folder Workspace is implemented in v0.1.
- TypeScript uses strict mode.
- Rust must not `unwrap()` user-controlled filesystem data.
- No completion claim without fresh verification evidence.
- Every task below ends in an independently testable deliverable and a focused commit.

# 0. v0.1 Scope Boundary

v0.1 must deliver exactly this user path:

```text
Launch app
  ↓
Choose local folder
  ↓
See folders and Markdown files in a tree
  ↓
Click a Markdown file
  ↓
Read it in Source Editor
  ↓
Edit
  ↓
Save
  ↓
File on disk remains ordinary Markdown
```

The following are explicitly deferred:

```text
v0.2  multi-folder Workspace, watcher, richer file operations
v0.3  Markdown preview/rendering
v0.4  split/live/Typora-like editing
v0.5  Properties, backlinks, Knowledge Object metadata
v0.6  LaTeX compilation
v0.7  SQLite/FTS indexing
v0.8  Knowledge View
v0.9  customization hardening
v1.5+ graph/plugins/git/database
v2+   AI/Canvas/sync providers
```

If an implementation step starts requiring one of these deferred systems, stop and simplify the design rather than importing future architecture early.

# 2. Core Interfaces Locked by v0.1

These interfaces are the only cross-boundary contracts v0.1 should stabilize.

## Rust → Frontend DTOs

```rust
#[derive(Debug, Clone, serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub struct FileTreeNode {
    pub name: String,
    pub path: String,
    pub kind: FileNodeKind,
    pub children: Option<Vec<FileTreeNode>>,
}

#[derive(Debug, Clone, serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub enum FileNodeKind {
    Directory,
    Markdown,
}

#[derive(Debug, Clone, serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub struct TextDocumentSnapshot {
    pub path: String,
    pub content: String,
    pub modified_at_ms: u64,
    pub size: u64,
    pub newline: NewlineStyle,
    pub has_utf8_bom: bool,
}

#[derive(Debug, Clone, serde::Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct SaveTextDocumentRequest {
    pub path: String,
    pub content: String,
    pub expected_modified_at_ms: u64,
    pub expected_size: u64,
    pub newline: NewlineStyle,
    pub has_utf8_bom: bool,
}

#[derive(Debug, Clone, serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub struct SaveTextDocumentResult {
    pub modified_at_ms: u64,
    pub size: u64,
}
```

## Frontend domain types

```ts

  name: string;

  path: string;
```

- [ ] **Step 3: Implement atomic writer**

Required sequence:

```text
validate path
→ read current metadata
→ compare expected mtime + size
→ encode editor text according to stored newline style
→ restore BOM if required
→ create temp file in same directory

→ sync temp file
→ atomically replace target
```

```markdown
# ADR 0001: Filesystem Access Stays Behind the Rust Boundary

## Context
The application edits real user files and must preserve local-first safety.

## Decision
React/TypeScript never performs unrestricted filesystem access. UI calls typed Tauri commands; Rust validates paths and performs I/O.

## Alternatives
- Tauri filesystem plugin exposed directly to UI
- Node/Electron filesystem access
- Database-backed documents

## Consequences
- Slightly more boilerplate

- Easier future permission model

## Migration
None for v0.1.
```

# 5. Risks to Watch During Execution

## Risk A — Tauri command names drift from TypeScript wrappers

Mitigation:
- wrapper tests assert exact command names;
- DTO tests assert serialized names.

## Risk B — Save code accidentally normalizes all files to LF

Mitigation:
- byte-level CRLF tests;
- newline metadata is part of snapshot.

## Risk C — BOM silently disappears

Mitigation:
- raw byte BOM fixture and writer tests.

## Risk D — External editor changes are overwritten

Mitigation:
- compare expected file metadata before save;
- conflict error prevents replacement.

## Risk E — “Atomic save” is only nominal

Mitigation:
- temp file in same directory;
- flush/sync;
- replacement only after complete write;
- failure-path test confirms original remains intact.

## Risk F — Frontend starts depending on system path semantics

Mitigation:
- frontend treats path as opaque string;
- Rust owns `Path` / `PathBuf`.

## Risk G — v0.1 gets bloated with future architecture

Mitigation:
- single root only;
- no Workspace schema;
- no DB;
- no graph;
- no parser stack;
- no preview;
- no plugin SDK.
